# Работа с репозиторием

В репозитории три независимо собираемых Go-сервиса. У каждого свой `go.mod`, конфигурация, `.env.example` и Dockerfile. Держи Docker-конфигурацию в каталогах сервисов. Инструкции по запуску и публичные маршруты описаны в [README.md](README.md).

## Где делать изменение

- `auth-service` владеет учётными записями и refresh-сессиями в `auth_db`. При выдаче access-токена в `sub` записывается ID сохранённого пользователя. Если меняется формат JWT, проверь также его обработку в `api-gateway/internal/api/middleware/user.go`.
- `ai-service` владеет ассистентами, чатами, сообщениями, каналами переписки, блокировками контактов и статистикой в `ai_db`. У ассистента `user_id` хранит ID владельца из Auth. Это межсервисная ссылка. Для запросов к данным владельца используй таблицы AI. Для связей между таблицами внутри одной БД используй её обычные ограничения.
- `api-gateway` — публичная точка входа. Здесь находятся проксирование, проверка пользовательского JWT и передача идентичности в AI. Шлюз работает без подключения к PostgreSQL. Правила работы с ассистентом или сессией размещай в сервисе, который ими владеет.

## Как добавить модуль или маршрут

1. Помести логику модуля в `internal/modules/<имя>` соответствующего сервиса. Передавай зависимости через конструктор. Для запроса к БД из HTTP-обработчика передавай `c.Request.Context()` по цепочке вызовов.
2. Создай долгоживущие зависимости в `main.go`. Там же управляй их жизненным циклом. Добавляй модуль в `internal/app.App`, когда API нужен к нему доступ. Если он нужен только другому модулю, передай его прямо в конструктор потребителя.
3. При регистрации маршрутов возьми из `App` нужные зависимости и передай их в конструктор обработчика. Пример в Auth — `main.go` создаёт `auth.New(db, cfg)`, а `internal/api/router.go` передаёт `a.Auth` в `handlers.NewAuthHandler`.
4. В AI добавляй маршрут в `internal/api/<область>/router.go`. Новую группу подключай в `ai-service/internal/api/routes.go`. Gateway уже проксирует кабинетные пути `/ai/*` со снятием префикса. Новый публичный webhook регистрируй явно и в AI, и в `api-gateway/internal/api/routes.go`.

## Доступ к ресурсам

- Для кабинета gateway очищает входящие заголовки идентификации, проверяет JWT и передаёт в AI доверенный `X-User-Id`. Доступ к личному ассистенту или чату проверяется в AI. Используй функции `access.Assistant` и `access.Chat` из `ai-service/internal/api/access/owner.go` либо запрос с условием по владельцу. Для WebSocket проверь доступ до открытия соединения. Список заблокированных SMS-контактов по текущему контракту глобальный.
- У внешнего API свой способ авторизации. В `POST /webhooks/telegram` клиент передаёт Bearer-токен ассистента, по которому AI находит ассистента. Для входящих событий Telegram используется отдельный путь `/webhooks/telegram/callback/:assistant_id`. Учитывай это различие при изменении маршрутов.

## Данные и проверки

- SQL-запросы храни в `internal/modules/database` сервиса-владельца. Для изменения схемы добавь следующий нумерованный файл в его `migrations/`, например `002_add_column.sql`. Сервис применяет файлы при запуске и запоминает их имена, поэтому редактирование уже применённого файла не обновит существующую БД.
- При изменении настроек обнови `internal/config` и `.env.example` затронутого сервиса. Изменения запуска и публичного контракта отрази в README.
- Отформатируй изменённые Go-файлы через `gofmt`. Из каталога каждого затронутого модуля выполни `go build ./...`, `go test ./...` и `go vet ./...`. Если меняется контракт между сервисами, проверь обе стороны. При изменении маршрутизации или передачи идентичности обнови подходящие сценарии в `api-gateway/internal/api/routes_test.go`.
- Для интеграционных тестов PostgreSQL укажи отдельную тестовую БД через `AUTH_TEST_DATABASE_URL` в Auth и `TEST_DATABASE_URL` в AI. Без этих переменных Go пропускает соответствующие тесты.
